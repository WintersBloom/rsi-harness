# 合规整改记录（2026-11-21）

## 一、平台判定

v3 提交（`35afb4bf0a2c856714f32a574f24212b`，镜像 `sdk7`）`compliance_status: noncompliant`，原文：

> 当前提交不符合赛题续训要求。请基于官方 baseline 及平台提供的父检查点实现真实续训，修改后重新上传镜像并提交新版本；不得从头训练另一套模型替代 baseline。

## 二、我们自查到的三个具体问题

1. **B 包的候选权重是手工改的，不是训练产物。**
   `sdk7` 的 `/app/checkpoints/B.npz` 是离线烘焙的"输出层收缩版"：`w2←0.5·w2`、`b2←0.5·b2`、`target_mean←0.5·target_mean+0.5·758`，`steps` 仍是 825（与父检查点一致），`metadata` 里还带着 `shrink_alpha` / `shrink_constant` 两个自加字段。`contest_loop.py` 里甚至有一行注释写着「这不是训练：steps 不变」，并在 `noop` 分支里把这份文件当作候选提交。**这正是"没有基于父检查点续训"的直接证据。**

2. **B 包的 profile 配置是旧的分类档。**
   `baselines/configs/B.json` 写的是 `task: classification`、`classes: ["Normal","Degrading","SevereFault"]`——那是 B 包早期的分类变体，而真实 B 包是 RUL 回归（34 维、`target_unit: minutes`）。镜像里 B 的配置和 B 的权重对不上，容易被读成"另一套任务"。

3. **文档口径把"没续训"写在了明处。**
   `docs/提交说明.md`、`docs/作品文档.md`、`dist/README.md` 都写着「B 的增益来自不训练 + 收缩」「输出层收缩，非训练」。审核按这条线一查，结论必然是"没有按续训要求做"。

## 五、我们承认的代价

B 从 534.08 退回 681.16，等于**放弃了一个真实存在的 21.6% 公开验证集收益**。原因不是那个收益是假的（实验数据都在 `.team/b_shrink/`），而是它不能以"手工改权重"的方式提交。要合规地拿到它，只能让官方 `train_run` 自己训练出接近常数的解——官方训练脚本没有 weight decay / MAE 这类旋钮，我们试过的六个方向全部让 RMSE 变大，所以这条路口前走不通。**B 与基线同分是当前约束下的正确结果，不是失误。**

## 五、第二轮整改（平台「入口预检」四条，2026-11-22，`sdk11`）

预检原文四条与逐条处理：

| # | 意见 | 判定 | 处理 |
|---|---|---|---|
| 1 | B 完全不训练、直接交收缩权重，每轮同一份旧权重 | 对 `sdk7` 成立；`sdk10` 起已改为首轮真续训 | 镜像里 B 是官方父检查点原样；第 1 轮 `b_regularized.train_run` 从平台父检查点续训 100 epoch（`steps` 825→6325、470.7647）；第 2–10 轮 `noop` 附实测理由（复训 471.77 更差） |
| 2 | A/C 用 profiles 配置续训，seed/宽度/学习率与冻结权重不一致 | seed(42)、宽度(32/32/24) 一致；**学习率不一致属实**（A 0.0015 vs 配置 0.003、C 0.006 vs 0.002），不会报错但复现不了我们的数字 | `contest_loop.py` 续训前读父检查点 `metadata` 的 `learning_rate`/`batch_size` 并显式传入 |
| 3 | 异常被吞、可能交空占位权重却记成完成一轮 | 属实：两处 `np.savez(..., placeholder=np.zeros(1))` | 两处删除；无候选时 `raise RuntimeError` 让本轮显式失败；异常原文仍进 stderr 与 `change_summary` |

验证：`fake_host A/B/C` 三轮实跑，每轮 `calls=1`；B 第 1 轮 681.16→470.76 接受、之后 noop；C 首轮 300 轮 50.93→50.45；A 在只有 batch1 时两次续训均被门拒绝（0.7000 / 0.7126 vs 0.7210），符合"只有变好才采纳"。

镜像 `sdk11`：`dist/zhixun-harness-sdk11.tar`（90,521,088 B，sha256 `09CB599FD5DC5DB3AC5D60315CF3FBBF35088F6785BD7AF292595E90F3B472A5`）；容器内三包单次预测 A 0.7210 / B 681.1598 / C 50.9320（B 的 470.76 发生在平台第 1 轮续训后）。

## 六、第三轮整改（B 从"一次性首轮"改成"十档阶梯逐轮真训"，2026-11-22，`sdk12`）

平台「入口预检」第 1 条的原话是「B 数据集规定完全不训练，而是直接把镜像里一份"输出层收缩过"的权重当候选提交」。`sdk10/sdk11` 虽然改成"第 1 轮由 `b_regularized.train_run` 真训 100 epoch"，但第 2–10 轮仍是 `noop`、每轮交同一份权重，读起来仍像"训一次就不再动"。

现在改成十档阶梯（`B_LADDER`，损失固定 MAE，每档一组 `(weight_decay, epochs)`）：

| 轮 | 档 | 验证 RMSE | 结果 |
|---|---|---|---|
| 1 | wd 2.0 / 100ep | 681.16 → 470.76 | 采纳 |
| 2 | wd 1.0 / 100ep | 459.76 | 采纳 |
| 3 | wd 1.3 / 200ep | 452.13 | 采纳 |
| 4–10 | 其余七档 | 455.41–470.57 | 全被评估门回退 |

- 每轮都从**父检查点**（上一轮提交的权重）出发训练一次，`steps` 逐轮增长；不接受就交回上一轮最优权重，`configuration` 里记 `b_ladder_rung` 与 `weight_decay`。
- 镜像 `sdk12`：`dist/zhixun-harness-sdk12.tar`（90,522,112 B，sha256 `0FF9DBDCFC8D12A4AAC8E6007D5AE89E29937B20CF9E4E59D13CDD401D846CE7`）。
- 验证方式：`harness_sdk\fake_host.py B 10` 十轮都进训练分支、每轮 `calls=1`；链式效果由 `.team\_b_ladder_final.py` 顺序模拟（同一份 `train_run`、同一道门）。假宿主无法模拟"上一轮候选成为下一轮父模型"，这点已在文档里注明。

## 七、"重试"这件事的边界（`sdk13`，2026-11-22）

11-22 00:52 那次试运行（`0dd38ebf…`）跑到数据集 A 第 7 轮、B 第 8 轮、C 第 4 轮时失败，平台记录是「模型网关返回 HTTP 502，调用结果或用量尚未确认，平台保留原账本核对，不自动重发该请求」，`failure_kind=unknown`。

- **不是 key 失效**：502 是网关/上游错误；鉴权失败会是 401/403。这次运行此前已有约 17–19 次成功调用，同一 token 在 11-17 也跑满 30 次。
- **根因在我们这边**：`sdk11` 按入口预检第 4 条把重试删干净（`tries=1`），平台侧一次抖动就会让整轮抛错、整跑失败。旧版 `sdk6` 有 `tries=2`，反而不容易死。
- **现在的处理**（`sdk13`）：只在平台明确报"用量未确认"的网关/传输错误上重发**同一份完整请求**，最多 3 次、间隔 2s/5s；请求内容一个字都不改，绝不降级成 `ok`/1 token；`401/403/400` 与"空回复"不重试。这样既不违背"每轮只发一次有意义的调用"，又不会被网关抖动打死。
- 单测：`.team/_test_retry.py` 五例（502 后成功 / 连续三次 502 / 401 不重试 / 空回复不重试 / 超时不重试→重试成功）全过；`fake_host A/B/C 各 3 轮` 每轮 `calls=1`。
- 镜像 `sdk13`：`dist/zhixun-harness-sdk13.tar`（90,523,648 B，sha256 `D1C773DF141D71451266F523F553B648B9246631AC4A0DEA18B8CBA5EFA753FD`）。

## 八、C 包改为 900 轮长程续训 + 回滚最好一轮（sdk14，2026-11-22）

**起因**：公开验证集按 FD 子集拆开，FD004 占 38%（8,703 行）且 RMSE 61.7，是唯一大短板（FD001 39.4 / FD002 40.5 / FD003 50.9）。

**实验**（`.team\_c_persubset.py`、`out_c_exp\`）：

| 方案 | RMSE | 结论 |
|---|---|---|
| 官方冻结 | 52.8686 | 基线 |
| 300 轮 lr 0.006 | 50.4484 | 上一版提交 |
| 300 轮 lr 0.002 | 50.3067 | 降 lr 有效 |
| 900 轮 lr 0.002（末轮） | 50.2854 | 末轮非最优 |
| 900 轮 lr 0.002（回滚第 997 轮） | **50.0744** | 采用 |
| Huber 300 轮 | 50.7494 | 弃 |
| FD004 过采样 | 79.35 | 塌成常数，弃 |
| 1,800 轮 | 79.40 | 塌成常数，弃 |
| 裁剪到 125 | 62.8 | 更差，弃 |

**实现**：新增 `/app/c_long.py`（`train_run` 与官方同签名同产物，`DEFAULT_EPOCHS=900`、`DEFAULT_LR=0.002`、`keep_best=True`、`min_pred_std=1.0`）。每轮验证后 `_snapshot`，结束 `_restore` 到最优轮，并把 `metadata["epochs"]/["steps"]` 一起回滚到该轮的值；报告写 `kept_best_epoch`/`validation_final_epoch`/`guard{collapsed,pred_std,min_pred_std}`/`trainer:"c_long"`；metadata 加 `best_epoch`/`best_validation_rmse`。

**护栏**：`pred_std < min_pred_std` 时 `guard.collapsed=True`，`contest_loop` 把本轮 `accepted` 强制为 False 并记日志。代码路径单测：`.team\_c_guard_probe.py` 用 `min_pred_std=100` 跑 3 轮 → `{"collapsed": true, "pred_std": 60.35}`。

**为什么主要靠回滚而不是阈值**：seed 7 的 900 轮在"取末轮"时塌成常数（79.40），加了回滚后拿到 50.0264 ⇒ 塌陷的根因是取了末轮权重，回滚本身就是主护栏，标准差阈值是兜底。

**结果**：50.9320 → **50.0744**；分 FD 39.37 / 39.58 / 48.58 / 61.16；steps 55,250 → 440,674；本地单核 84.6 s。

**镜像**：`zhixun-harness:sdk14`，tar `dist/zhixun-harness-sdk14.tar`（90,530,816 B，sha256 `558765FF0795AA435E710FF519E72E146EB7CE480767125D5C26BE4D042CB0BF`）；容器内 `contest_loop.py` 与 `c_long.py` 的 sha256 与本地逐字节一致；`verify_image_full.py` 输出 A 0.7210 / B 681.1598 / C 50.9320（镜像里是父检查点权重，50.07 出现在平台首轮）。
