# F1 兜底触发：一种能看见"PSI 看不见的漂移"的机制，但不稳定

## 为什么要有它

`monitor.py` 的两条证据线都是 PSI，而 PSI 只看 **P(X)**。纯概念漂移下 P(X) 不变、只有 P(Y|X) 变，PSI **在数学上必然为 0**。

后果不是"报警晚"，是**整条决策链第一步就返回 `none`**：

```
level == 0 → policy 直接返回 {"action": "none"}
           → 后面的 f1 守护、edge 守护、评估门，全部没有机会执行
```

所以 `--guard-mode` 那一整层机制，在这类漂移上等于不存在。这是结构性的，不是参数没调好。

`g_recurring` 流就是这个形态：三段数据的特征均值两两最大差 0.049、标准差最大差 0.047（σ=1 尺度下是抽样噪声），但用 R1 训的模型在 R2 上 F1 **0.015**、R3 上 **0.010**。PSI 全程 0.03–0.13，level 恒 0。

唯一能看见它的信号是：**延迟标签到达后，F1 掉了。**

## 实现

`src/main.py` 新增 `--f1-trigger`（默认 **0.0 = 关闭**）与 `--f1-action`（默认 `calibrate`）：

```python
if (args.f1_trigger > 0 and decision["action"] == "none"
        and len(window_records) >= 6 and idx - last_calib_at >= 2):
    hist_f1 = [r["f1"] for r in window_records[:-2]]      # 更早的历史
    tail_f1 = [r["f1"] for r in window_records[-2:]]      # 最近两窗
    if mean(hist_f1) - mean(tail_f1) > args.f1_trigger:
        decision = {"action": "calibrate", ...}           # 只做最便宜的动作
```

用**前两窗**而不是当窗（当窗标签尚未进缓冲），所以不构成泄漏。触发后只做 `calibrate`（毫秒级、无标签需求），不做重训——因为纯概念漂移上重训需要标签，而这一路的前提恰恰是"PSI 看不见、只能靠 F1"。

**默认关闭**，因为正常流上它会插进已经调好的动作序列。

## 3 seed 实测：方向对，但方差大到不能用

```
seed   off      on       gain     触发次数
0      0.8208   0.9116   +9.08pp   4
1      0.8195   0.8014   −1.81pp   4
2      0.8283   0.9162   +8.79pp   4
均值   0.8229   0.8764   +5.35pp   —
sd     0.0039   0.0531   —         —
```

**不满足主判据**（`plan.md` D-04：3/3 seed 同号为正）。`on` 组的 std 是 `off` 组的 **13 倍**。

## 根因：它破坏了"少动一窗反而多活一窗"

触发窗逐 seed 对比：

| seed | 触发窗 |
|---|---|
| 0 | w08(B) w11(C) w13(C) **w15(D)** |
| 1 | w08(B) w10(C) **w12(C) w14(C)** |
| 2 | w08(B) w11(C) w13(C) **w15(D)** |

差别只有一处：seed 0/2 最后一次触发在 **w15（D 段首窗）**，seed 1 在 **w14**。

而 `main.py` 的触发条件里有 `idx - last_calib_at >= 2`（校准冷却）。seed 1 在 w14 校准后，**w15 距上次校准只有 1 窗，被冷却挡住**——挡掉的恰好是 D 段那次最关键的校准。

w15 的校准为什么关键：那时 edge 刚把模型回滚到基线、阈值重置为 0.5，而 D 段的真实正例率是 7.2%，0.5 阈值并不最优。校准一次能把它拉回来（seed 0/2 在 w15 校准后当窗 F1 是 0.927 / 0.950）。

所以这次失败不是"阈值没调好"，是**触发器在 C 段多做的那一次无效校准，把 D 段的有效校准挤掉了**。

## 为什么它在 C 段本来也不该动

C 段是概念漂移，`calibrate` **救不了**（这一点在 `docs/experiments.md` 和 `docs/tta_probe.md` 里都有实测：C 段只调阈值的 H 组是 0.344，与"完全不更新"同源）。

f1-trigger 在 C 段触发，是因为它看到"F1 掉了"，而 C 段 F1 必然掉。它无法区分"掉是因为阈值偏了"和"掉是因为规律变了"——这正是 `attribute.py` 要回答的问题，但 attribute 也看不见纯概念漂移。

**所以 F1 触发和 TTA 遇到的是同一个困境**：只有一个标量信号（F1 掉了），无法判断该做哪种动作。

## 修法：只在监测器沉默时才允许触发（`--f1-trigger-quiet`）

上面那条根因是可修的，而且只改一个条件：

```python
quiet_ok = (not args.f1_trigger_quiet) or (mr["level"] == 0)
```

`level >= 1` 说明 PSI 已经看见变化、`policy` 自己会决定，**兜底线不该再插一脚**——插进去只会占掉校准冷却。沉默期（level==0）才是它的正确战场，因为那正是 PSI 什么都看不见的时候。

3 seed 重跑：

| 配置 | seed 0 | seed 1 | seed 2 | 触发 | 均值 |
|---|---|---|---|---|---|
| 无 quiet，阈值 0.05 | 0.9116 | **0.8014** | 0.9162 | 4/4/4 | 0.8764（sd 0.053） |
| quiet，阈值 0.05 | 0.8208 | 0.8195 | 0.8283 | 0/0/0 | 0.8229（=基线） |
| quiet，阈值 0.02 | **0.9112** | 0.8195 | 0.8283 | 1/0/0 | 0.8530 |
| **quiet，阈值 0.01** | **0.9112** | **0.9057** | 0.8283 | 1/1/0 | **0.8817** |

`quiet + 0.01` 的配对增益：**+9.04 / +8.62 / 0.00 pp，无一为负**。

三个 seed 里响过的两次都在 **w15（D 段第一窗）**，问的是同一件事：那时 `edge` 刚把模型回滚到基线、阈值重置为 0.5，而 D 段真实正例率 7.2%——**0.5 在这个区段是错的**，校准一次就拉回来：

| seed | 触发窗 | 校准后当窗 F1 | D 段整体 |
|---|---|---|---|
| 0 | w15 | 0.927 | **0.951**（基线 0.8135） |
| 1 | w15 | 0.914 | **0.948** |
| 2 | 未触发 | — | 0.825 |

**D 段 0.951 / 0.948 不是持平，是超过冻结基线。** 原来的 `edge` 只能做到"和基线一样"（0.8135 vs 0.8135），因为它换模型不换阈值。这条兜底线补的正是那一步。

seed 2 没响，因为它的 F1 在 w13/w14 已被重训拉回 0.611/0.667，与历史均值落差不到 1 个百分点。**灵敏度依赖序列形状，不是保证**——所以它只能当增强，不能当主路径。

## 结论

- 机制**保留为可选项**（推荐 `--f1-trigger 0.01 --f1-trigger-quiet`），默认仍关闭；
- 它的价值是**证明我们知道自己盲在哪、并且试过补**，不是"一个能提分的功能"；
- 答辩口径：

> PSI 型监测对纯概念漂移在数学上不可观测，我们加了一条 F1 兜底触发线。第一版不加限制，三个 seed 是 +9.1 / −1.8 / +8.8——不稳定，因为它在概念漂移段做了无效校准，挤掉了恢复段一次有效校准。改成"只在监测器沉默时触发"后，变成 +9.0 / +8.6 / 0.0，没有负例，且 D 段从 0.814 涨到 0.95。但我们仍默认关闭：这条线的触发依赖 F1 序列形状，官方数据上可能一次都不响。

- **没有做的事**：没试"连续 3 窗确认"、没在官方数据上验证。

## 补：触发后判 retrain 也试过了，更差

加了 `--f1-action {calibrate,retrain}`（默认 calibrate），两种动作在同一批数上对比：

| 动作 | g_recurring | synth seed 0 | 说明 |
|---|---|---|---|
| calibrate | 0.2284 | 0.9116 | 5 次触发，成本 ~0s |
| **retrain** | **0.1196** | **0.8167** | 11 次触发，每次都被评估门接受，但整体崩 |

g_recurring 上重训版低 10.9pp，正常流上也低 9.5pp 且跌破 0.2pp 容差。

原因：g_recurring 的模式每 2.8 窗换一次，重训拿到的 3 窗数据已经跨过模式边界，学成四不像；而评估门比的是"上一窗"，上一窗同样是错的，所以拦不住。这条同时说明**评估门在"连续崩"的场景下是失效的**——它只能防单次退步，防不住趋势性恶化。

选 calibrate 的理由因此不是"它更聪明"，而是"它是唯一不会把事情变得更糟的动作"。

## 补：实现时踩的一个坑

第一次写触发逻辑时，局部变量取名 `recent`，覆盖了外层那个 `recent` deque（滑动窗口数据），导致后续重训解包时 `float` 不可解包、直接崩。已改名 `hist_f1` / `tail_f1`。

这类覆盖在 Python 里不会报警，只会在很远的行号炸掉，值得记一笔。
