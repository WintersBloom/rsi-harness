## 1. SDK 里两条"还没写记录就退出"的路径

这两条是**结构性的**，不是猜测——源码里写死在抛出点上。

| 路径 | 触发条件 | 后果 | 证据（文件:行） | sdk5 / sdk6 是否已堵 |
|---|---|---|---|---|
| `MODEL_CALL_REQUIRED` | `finish()` 时 `cited_calls` 为空 | 整轮作废，平台收不到 `round_complete` | `contest_harness/round.py:336-337`；`round.py:188` 只有**调用成功**才 `call_ids.append` | sdk5 新增 `_bank_call` 三级重试（900 → 1 → 固定 `ok`），保证至少一次成功回执 |
| `HISTORY_INVALID` | 平台 history 记录不符 `id` 校验 | 整轮作废 | `round.py:151-163`；原 `contest_loop.py` 的 `rnd.history()` 在 try 之外 | sdk5 删除 `rnd.history()`，`finish()` 只传 `model_call_ids=list(rnd.call_ids)` |
| 决策/执行段未捕获异常 | 任何未捕获异常 | 进程退出，无 `round_complete` | sdk4 及以前 | sdk5 起决策、执行、提交三段全包 try，异常写 `fatal=` 进 `change_summary` |

## 2. 失败后按 stderr 定位（sdk6 起可读）

sdk6 在 `contest_loop.py` 里每轮打**四行**日志到 **stderr**，失败时另打一段 `traceback` 全文（协议帧走独立 fd，二者物理隔离，见 `contest_harness/protocol.py:36-42` 与 `cli.py:51/59/71` 的 `isolate_stdio()`）。

| 观测到哪一行 | 死在 | 下一步 |
|---|---|---|
| 一行 `[zhixun]` 都没有 | 容器未起 / `describe` 未通过 | 查镜像启动耗时、`/app/harness.py` 路径、SDK 挂载 |
| `start` 有，`decide` 无 | 模型调用段 | 看 `llm_status`、`call` 是否为空；对照 `docs/pytrio接入.md` 第 6 节 |
| `decide` 有，`train epochs=` 无 | 训练前准备（父模型、候选目录） | 看 `parent_found`、`/workspace` 是否可写 |
| `train epochs=` 有，`submit` 无 | 训练超时或异常 | 看 epochs 与耗时；C 包单轮 14.40 s 已贴近 15 s 边界 |
| `submit` 有仍失败 | 产物 / 协议层 | 看 `artifact`、`calls`、`fatal` |
| 见到 `traceback` 全文 | 已捕获的异常 | 栈顶第一行即崩溃点；与 `change_summary` 里的 `fatal=` 对照，两处应指向同一行 |

## 4. B 包：官方权重与其验证曲线

**事实**

- 官方 `checkpoint.npz` 的 metadata：`epochs=15`、`initial_epochs=None` ⇒ 从零训练 15 轮的产物。
- 同包 `history.jsonl`（15 行）：第 2 轮 `validation.rmse = 567.1475`，第 15 轮 `validation.rmse = 681.1598`。
- 我们在 `public/validation.jsonl`（1679 条 / 3 根轴承）上复算该权重，RMSE = **681.1598**，与第 15 轮记录逐位一致 ⇒ 同一验证集、同一定义。

**解释**

我们试过的六个续训方向全部劣于 681.1598，且验证集 RMSE 随 epoch 单调恶化的形态，与该起点已处于过拟合后段这一解释**一致**。这是解释，不是结论：该验证集仅 3 根轴承、`Bearing3_4` 占 1515/1679，无法推断隐藏测试集上的表现。

**不可执行**

第 2 轮权重未随包发布；从零重训至第 2 轮不构成"从官方 baseline 续训"——产物的 `parent_checkpoint_sha256` 为空，平台公告明确禁止"从头训练冒充续训"。因此该路径在规则内不可执行，只能写入报告的已知限制。

## 5. 本表不能证明的事

- 平台侧日志（我们无权读取）：容器是否启动、启动用了多久、SDK 是否握手成功。
- 平台"15 秒"的真实含义（单轮上限？首帧等待？兜底超时？）：目前只有两次转述，SDK 源码里没有任何 timeout 常量。
- 镜像在平台机器上的真实冷启动耗时（本地 5.46 s 不能外推）。

## 6. 使用顺序

1. 点一次 sdk6 试运行（剩 9 次，只当探针，不看分数）。
2. 拿到 stderr 的五行日志。
3. 对照第 2 节，定位死在哪个阶段。
4. 对照第 3 节，判断是否属于"超时"而非"报错"。
5. 需要问管理员时，附本表第 0 节的时间线与第 2 节的定位结果，问题会具体得多。
