# 大模型调用：能不能“少调”？（给执行者的判断依据）

## 一、先给结论

你说的“进新轮次调一次、之后不确定才调”，**在平台规则下已经是我们的现状，而且不能再少**：

- 我们每轮（每个包的每轮）本来就**只调一次**，30 次 = 10 轮 × 3 包，正好是地板。
- 再少一次，`round_complete` 就会因为引用不到本轮 call_id 直接抛 `MODEL_CALL_REQUIRED`，整轮失败。

所以“解决大模型调用”这件事，能动的只有三处：**每次更便宜 / 每次更稳 / 让模型少做、规则多做**。次数动不了。

## 二、规则依据（`harness_sdk/app/contest_harness/round.py`）

| 行 | 代码 | 含义 |
|---|---|---|
| 134 | `self.call_ids = []` | 每个 Round 自己清零，**上一次的 call_id 带不过来** |
| 188 | `self.call_ids.append(call_id)` | 只有**成功**拿到响应才记一笔 |
| 335-337 | `if not cited_calls: raise HarnessError("MODEL_CALL_REQUIRED")` | 交卷时必须引用本轮的调用 |
| 342 | `if any(item not in self.call_ids ...): raise HarnessError("MODEL_CALL_UNKNOWN")` | 引用别的轮的 call_id 也无效 |

推论：**“这一轮不调、下一轮补上”不成立**；一轮不调 = 这一轮判失败。

另外，用“发一个只有一两个字的请求”去凑 call_id，正是平台入口预检第 4 条明令禁止的（原文：*为拿调用凭证而凑数*）。所以也不能用空包占位。

## 三、真正没解决的是“调用质量”，不是“调用次数”

两次运行里 30 次调用的实况（按包统计空回复）：

| 版本 | max_out | answered | prompt | completion | 空回复分布 |
|---|---|---|---|---|---|
| 正式 #1（sdk15） | 900 | **28/30** | 20,170 | 13,012 | A 0 / B 1 / C 1 |
| sdk16 试运行 | 320 | **19/30** | 16,588 | 7,458 | A **6** / B **5** / C 0 |

- A 在 sdk16 掉 2pp，根因就是 A 有 6/10 轮拿不到答案、退回规则层，第一轮就选了 `retrain_20`（正式 #1 是 `retrain_10`），之后动作序列整个不同。
- **空回复并不省钱**：思考照样按 completion 计费（每次仍 ~250 token），只是答案没出来——等于花 250 token 买了个静音。
- C 在 320 下 10/10 都答得出来 ⇒ 不是“320 一定不够”，而是**同样的上限对 A/B 的候选集经常不够**（候选多、理由要求长）。

## 四、三条可选路线

| 方案 | 估计 token | answered | 决策质量 | 代价 |
|---|---|---|---|---|
| A. 维持 `max_out=320` + 新提示词（已改） | ~21,000 | 19/30，短提示可能升到 22–24 | 1/3 轮次走规则 | 零成本，已改完 |
| B. `max_out` 回 700 + 新提示词 | ~29,000 | 预计 27–29/30 | 全轮由模型选 | 多 8k token（效率分约 −0.3） |
| C. 换 `Qwen/Qwen3.5-4B` + 320 | ~15,000–18,000 | 未知 | 可能略降 | 要新建提交、烧一次试运行 |

## 五、建议

倾向 **B（回 700）**，理由是把两边的账算清：

- 空回复带来的 A 掉分：−2pp × 归一化权重 ≈ **−0.5～0.7 分**
- 省 8k token 带来的效率分：我们已经在 2/5，最多挪到 3/5 ⇒ **+0.3 分左右**
- 也就是说：**为了省 token 而让模型答不出来，是亏的**。

折中做法：先按 A（320 + 新短提示）跑一次 sdk17 试运行，看 A 包的空回复从 6 降到几；若仍 ≥4，下一次直接切 700。

一句话：**次数是死的（30 次），能调的是“每次买到的答案值不值”。**
