# 镜像设计：一个镜像跑三个任务（可行，已实测）

## 一、三种输入 schema 完全不同（逐包实测第一行）

```jsonc
// A：features 是长度 128 的定长数组
{"id":"gas_b02_000001","inputs":{"features":[21749.5635, 2.627488, ...]}}

// B：features 是对象，分 horizontal / vertical，各 17 个具名字段
{"id":"xjtu_Bearing1_4_s000001",
 "inputs":{"features":{"horizontal":{"rms":0.4624,"peak":1.6891,"kurtosis":2.9443,...},
                       "vertical":{...}}}}

// C：没有 features，是 settings(3) + sensors(21)
{"id":"fd001_train_u0071_c00001",
 "inputs":{"settings":[0.0027,-0.0004,100.0],
           "sensors":[518.67,642.64,1581.95,...]},
 "answer":207,
 "meta":{"source_subset":"FD001","source_split":"train","unit":71,"cycle":1,...}}
```

**路由判据（只看键名与类型，不会误判）**：

```python
def route(inputs):
    if "settings" in inputs:                          # C
        return "C"
    f = inputs.get("features")
    if isinstance(f, dict):                           # B
        return "B"
    if isinstance(f, list) and len(f) == 128:         # A
        return "A"
    raise ValueError("unknown input schema")
```

`task` 字段不能用来路由——**B 和 C 都是 `"regression"`**。只有 schema 能区分。

## 二、共用与不共用

| 层 | 共用？ | 说明 |
|---|---|---|
| 输入解析与路由 | ✅ | 上面 8 行 |
| 五环骨架（监测→归因→决策→执行→回滚） | ✅ | 逻辑一致 |
| 预算 / 冷却 / 次数闸 | ✅ | 参数可不同 |
| **评价函数** | ❌ | A：Macro-F1；B/C：RMSE（C 另报 NASA 非对称分） |
| **校准方式** | ❌ | 分类挪阈值；回归加偏置常数 |
| **模型与标准化参数** | ❌ | 三套 checkpoint |

目录结构：

```
harness/
├── predict.py        # stdin → route → 前向 → stdout
├── core/             # 五环（共用）
└── tasks/
    ├── a/checkpoint.npz + config.json
    ├── b/checkpoint.npz + config.json
    └── c/checkpoint.npz + config.json
```

三个 checkpoint 合计约 400 KB，整个镜像仍然远低于 2 GB。

## 三、状态必须按任务分桶

五环是有状态的，三套状态绝不能串：

```python
state = {}
st = state.setdefault(task, new_state())   # 各自的窗口、历史指标、冷却计数
```

三套状态合计几十 KB，内存不是问题。**但串了就是灾难**：A 的"连续 3 窗报警"记到 C 上，会让 C 无端重训。

## 四、一个必须记住的红线（实测确认）

`validation.jsonl` 里带着 `answer` 和 `meta`，**`meta` 里有 `unit`、`cycle`、`source_subset`、`source_batch`**。

这些字段在数据里存在，但 `TASK.md` 明确禁止当特征（C 包尤其："不能使用未来循环"、不能把 unit/cycle 拼进输入）。

**在镜像里必须显式丢弃 `answer` 与整个 `meta`**，只取 `inputs`。这不是"不用就行"，是"要写成代码里的白名单"——否则将来有人为了调模型把 meta 加进去，就是标签泄漏。

## 五、一次提交跑三个包（由表单字段推出，非官方明示）

平台提交表单只有七个字段：`model`、`model_source`、`api_key`、`training_url`、`source_url`、`image_archive_id`、`document_id`。

**没有任何一个字段问"你提交的是 A 还是 B 还是 C"。**

如果一次提交只对应一个包，就必须有"数据集"下拉框；没有，就只能解释为：

> **一次提交 = 一个镜像 = 同时跑三个包。**

于是评测结构是：

```
提交一个镜像
  → A 隐藏流 → Macro-F1
  → B 隐藏流 → RMSE（分钟）
  → C 隐藏流 → RMSE（循环）+ NASA 分数
  → 三者各占 1/3
```

**推论 1：6 小时墙钟是三个任务共享的，平均每个约 2 小时。**

这个推论改变性能预算。以 B 为例：7032 行训练 + 1679 行验证只花 0.22 秒，所以即使跑十轮也远不到 2 小时；C 的 113 089 行 × 5 epoch 也只 0.58 秒。**真正的耗时不在训练，而在启动与 IO**。

**推论 2：预算闸要按任务各自独立，不能共用一个池。**

否则 A 把 15% 的额度用光，B/C 就一次都不敢动——而 B/C 恰恰是"续训就有收益"的两个。

**推论 3：三个 checkpoint 都得在镜像里，启动时按需加载。**

合计 400 KB 左右，全部预加载也只要一瞬。

⚠️ 上述结论来自表单字段的推断，**不是官方书面说明**。提问仍然值得发（问错不亏，问对省事），但不必等答复才开始打包——按"一个镜像跑三个"设计，即使实际是分开提交，也不会白做。

## 六、路由逻辑实测（全量验证，零误判）

在三个包的**全部** validation 记录上跑上面那段 `route()`：

| 包 | 记录数 | 路由结果 | 误判 |
|---|---|---|---|
| A | 1 244 | 全部 `A(128)` | **0** |
| B | 1 679 | 全部 `B` | **0** |
| C | 23 049 | 全部 `C` | **0** |

⇒ 判据是靠键名与类型，不依赖任何数值，换隐藏测试流也不会失效（除非官方改了 schema，那种情况本来就要重做）。
